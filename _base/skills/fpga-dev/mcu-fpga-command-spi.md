# Командный канал МК → ПЛИС (SPI, mem_target)

Справочник по протоколу команд STM32 → ПЛИС на R120M.BM2BF1X1 и по тому, как
его читать анализатором. Разобрано на железе 23.07.2026 (DSView, зеркало шины
на отладочных пинах).

## Физика

На BM2BF1X1 командный канал висит на пинах SSPI (`use_sspi_as_gpio`), ПЛИС —
slave: `SSPI_CMD_SCK` C10, `SSPI_CMD_MOSI` T10, `SSPI_CMD_MISO` M8,
`SSPI_CMD_CS_N` N9. Декодер: SPI mode 0 (CPOL=0/CPHA=0), MSB first, CS
active-low, триггер по спаду CS.

Зеркало шины для анализатора выведено в прослойке платы на X14:
`E1`=SCK, `E2`=MOSI, `F1`=CS#, `F2`=MISO (выпуск `R120M.BF2MF5FP1X3`).
При этом E1 переведён из входа в выход, а UART-телеметрия ушла на X1/FPGA_TX.

## Формат кадра (29 байт)

Реализация — `src/MCU_FPGA/mem_target/mem_target/mem_target.sv`.

| Смещение | Байт | Смысл |
|---|---|---|
| 0 | RW | `01` = запись, `00` = чтение |
| 1..4 | адрес | uint32 little-endian |
| 5..20 | данные | ровно 16 байт (для записи) |
| 21..24 | CRC | от МК; **ПЛИС его не проверяет** |
| 25..27 | dummy | ПЛИС отдаёт magic `55 AA 77` |
| 28 | dummy | ПЛИС отдаёт `error_code` |

Запись применяется НЕ по последнему байту данных, а в самом конце кадра:
`data_and_addr_vld_stb` взводится в `s_STATE_8`, то есть после CRC+magic+err.
Не дослал МК хвост — запись не применилась вовсе.

FSM сбрасывается только по подъёму CS (`end_transaction_stb`), внутрикадровой
защиты по таймауту нет.

## Карта адресов

`src/MCU_FPGA/interface_MCU_FPGA.svh`. Колонка «байты» — то, что видно на
анализаторе сразу после байта RW.

| Байты | Адрес | Регистр | Обработан в ПЛИС |
|---|---|---|---|
| `E8 03` | 1000 | MAC (12 Б) | да |
| `F8 03` | 1016 | IP (8 Б) | да |
| `08 04` | 1032 | UDP-порты потока (4 Б) | да |
| `18 04` | 1048 | угловое разрешение, мград | да |
| `28 04` | 1064 | температура около ВЦП | да |
| `38 04` | 1080 | LEDS | да |
| `48 04` | 1096 | STATE (keepalive) | **нет ветки в case** |
| `58 04` | 1112 | NTP-время | да |
| `68 04` | 1128 | был MIRROR_COMPENSATION, удалён | нет |
| `78 04` | 1144 | DBG | ветка пустая |
| `88 04` | 1160 | MIRROR_ALLOW_FIRE (4×1 бит) | да |
| `98 04` | 1176 | смещение энкодера, мград | да |
| `A8 04` | 1192 | задержка распространения, пс | да |
| `B8 04` | 1208 | запись таблиц компенсации | да |
| `C8 04` | 1224 | сектор обзора | да |
| `D8 04` | 1240 | параметры эха MSOP | да |

Примеры реальных кадров (23.07.2026): `01 88 04 00 00 · 01 01 01 01 …` —
разрешить выстрел на всех четырёх зеркалах; `01 38 04 00 00 · 03 …` — зажечь
светодиоды; `01 48 04 00 00 · 85 …` — keepalive STATE, в ПЛИС не обрабатывается.

## Режим SPI: слейв ждёт mode 1

**Слейв командного канала защёлкивает MOSI по СПАДУ SCK** — это SPI mode 1
(CPOL=0, CPHA=1). Так задано в `SPI_Slave.sv` (`SPI_MODE = 1` по умолчанию), так
же настроен эталонный `SPI_slave_overhead_tb`, и с этим режимом работала плата с
одними TDC7201. Режим протянут параметром `CMD_SPI_MODE` через
`MCU_FPGA` → `spi_mem_target`; значение по умолчанию 1 менять не следует.

Если мастер шлёт **mode 0** (меняет MOSI по спаду, ждёт чтения по фронту), слейв
ловит уже следующий бит и весь кадр уезжает на бит влево:

| Что на шине | Что видит ПЛИС |
|---|---|
| адрес `38 04 00 00` = 0x438 | 0x870 |
| байт данных `0x08` | `0x10` |
| байт данных `0x0A` | `0x14` |

Ветка нужного адреса в `case` не срабатывает, регистр не обновляется, светодиод
мёртв. Коварство в том, что **кадр при этом выглядит здоровым**: строб конца
кадра взводится, ответ `55 AA 77 65` уходит выровненным (TX сдвигается по спаду
и мастеру в mode 0 читается верно), на анализаторе байты декодируются красиво.
Расхождение видно только внутри ПЛИС.

Проверяется одним прогоном `src/main/R120M_BM2BF1X1_cmd_spi_tb.sv`: он подаёт
снятый с железа кадр обоими режимами мастера — mode 1 обновляет регистр,
mode 0 даёт адрес 0x870 и неизменный регистр. Правится НА СТОРОНЕ МК
(решение пользователя 23.07.2026): STM32 SPI master — `CLKPolarity = LOW`,
`CLKPhase = 2EDGE`.

## Слейв тактируется системным clk, а не SCK

`SPI_Slave.sv` не использует `SCK` как тактовый сигнал: линии `SCK` и `CS`
передискретизируются `edge_detector`-ами от системного `clk`, вся логика сдвига
построена на `always @(posedge clk)`, и в заголовке модуля оговорено требование
`clk` не менее чем вчетверо быстрее частоты шины (отсюда же потолок «слейв
держит такт не выше clk/4»).

Следствие, полезное при проектировании проверок живости: **сам факт внятного
ответа по командному каналу уже доказывает, что системный такт ПЛИС жив**. При
остановленном `clk` слейв не обнаружит ни одного фронта и не выдаст ничего.
Поэтому отдельный «свободно бегущий счётчик» в ответе для доказательства
тактирования избыточен — достаточно, чтобы ответ был ВЫЧИСЛЕН из присланного
значения, а не был константой (см. ниже про `55 AA 77 65`).

## Ловушки, проверенные на железе

- **Ответ `55 AA 77 65` НЕ доказывает, что команда принята по смыслу.**
  `error_code` инициализируется 101 (`ANS_OK`) и больше нигде не меняется:
  константы `ANS_CRC_ERR`/`ANS_ADDR_INVALID`/`ANS_WRITE_ERR` объявлены, но не
  присваиваются, CRC отбрасывается. Ответ подтверждает только то, что ПЛИС
  досчитала 29 байт кадра.
- **МК держит CS низким почти постоянно.** Замер: ширина CS-low 1.146885 мс при
  периоде 1.148745 мс — duty 99.84%. Внутри кадра пауза ~1 мс: МК шлёт
  RW+адрес+данные, молчит, потом досылает CRC/magic/err. Шина свободна ~1.9 мкс
  на кадр, окно ресинхронизации FSM — только это время. Потеря такта SCK внутри
  паузы уводит счётчик байт, запись ляжет по чужому адресу, а ответ всё равно
  придёт `55 AA 77 65`.
- **1.148745 мс — это период ОДНОЙ транзакции, НЕ темп полезных пакетов.** За
  100 мс МК успевает отправить ~87 транзакций на шине, но пакеты команд идут
  10 Гц (подтверждено кольцевым счётчиком LEDS, см. ниже). То есть на один
  пакетный такт приходится несколько записей регистров; не путать частоту
  дёрганья CS с частотой пакетов.
- `MEM_BYTES = 500` в `MCU_FPGA.sv`, поэтому адреса ≥1000 в теневую память не
  пишутся; работает только «атомарный» путь `addr_u32` + `data_16b` через `case`.

## Кольцевой счётчик МК в регистре LEDS

Главный факт, снятый анализатором 23.07.2026: **6-й байт кадра `LEDS` (адрес
1080) — это кольцевой счётчик**, а не битовая маска светодиодов. Три захвата
подряд дали `0x03` → `0x05` → `0x06`; между кадрами `0x03` (метка ~228.7 мс) и
`0x06` (~530.3 мс) прошло ~301.6 мс на 3 инкремента, то есть шаг ~100.5 мс —
**10 Гц**, ровно периодичность пакетов от МК.

Отсюда индикация строится выбором бита счётчика. Бит N переключается каждые
2^N тиков, полный период моргания — 2^(N+1) тиков по 100.5 мс:

| Бит | Период моргания |
|---|---|
| 0 | 0.2 с |
| 1 | 0.4 с |
| 2 | 0.8 с |
| 3 | 1.6 с |
| 4 | 3.2 с |
| 5 | 6.4 с |

**Брать только `if_mcu_fpga.leds`** — он обновляется исключительно кадрами
`LEDS`. Если защёлкивать первый байт кадра ЛЮБОГО адреса (так было в выпуске
X6), в индикацию влезают чужие регистры: константы из `STATE` (`0x85`) и
`MIRROR_ALLOW_FIRE` (`0x01`) роняют бит на один пакетный такт ~0.1 с, и вместо
меандра светодиод горит с короткими провалами. Симптом «горит и тухнет на пятую
часть секунды» — это именно он.

## Светодиоды: что чем управляется

Правило (уточнено пользователем 23.07.2026): светодиодом управляет ИМЕННО ПОЛЕ
КОМАНДЫ, а не активность шины. Индикаторы вида «пакет пришёл» или «бит счётчика
кадров» для этого не годятся — они светятся и при неверно разобранных данных.
Выпуски X4..X7, где LED5 моргал от строба разбора и от битов счётчика, сняты.

| Светодиод | Источник | Смысл |
|---|---|---|
| `FPGA_LED5` | `if_mcu_fpga.leds[LED_CNT_BIT]` | бит 3 6-го байта команды `3804` — моргание 1.6 с (выпуск X12) |
| `FPGA_LED4` | `if_mcu_fpga.leds[0]` | бит 0 того же байта |
| `FPGA_LED3` | `tdc_dev_state == 3` | LTDC-X3 откалиброван |
| `FPGA_LED2` | `MCU_FPGA_0` | активность линии МК |
| `FPGA_LED1` | heartbeat | ПЛИС жива |

Тракт до светодиода короткий и весь подтверждён: МК шлёт команду по адресу
`3804` (1080, `LEDS`) → ПЛИС кладёт её 6-й байт в `if_mcu_fpga.leds` → прослойка
разводит биты на пины.

**ПО в этом тракте НЕ участвует** (уточнено пользователем 23.07.2026): пакет
`3804` МК формирует самостоятельно с периодом 10 Гц, а его 6-й байт — собственный
кольцевой счётчик МК. Поэтому:

- не приписывать этому кадру ПК-команду «Отладка» 0x43 — связь не прослежена и
  её нет (ошибка разбора 23.07.2026);
- не искать в байте «состояние от оператора»: значения `03` → `05` → `06` — это
  просто счётчик, значение `04` не попало в захват;
- индикация строится ПРЯМЫМ выводом бита этого байта (`if_mcu_fpga.leds[N]`), а
  не внутренним счётчиком ПЛИС. Такой светодиод моргает только пока МК шлёт
  пакеты И ПЛИС разбирает их корректно — это и есть физическая проверка тракта.
